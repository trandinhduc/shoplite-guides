# 4.6 - Thiết kế kiến trúc cho tính năng với `/bmad-architecture`

**Thời lượng:** 30 phút · **Kết quả:** `ARCHITECTURE-SPINE.md` gồm các quyết định `AD-n` (có ràng buộc
kiểm chứng được), quy ước nhất quán, stack đã pin phiên bản, sơ đồ cấu trúc - qua được lint và reviewer.

## Lý thuyết nhanh: "spine" chứ không phải tài liệu kiến trúc dài

BMAD v6.12 không viết `architecture.md` dài vài chục trang. Nó viết một **architecture spine**: chỉ ghi
**quyết định**, không ghi lý do (lý do nằm trong `.memlog.md`). Tiêu chí đưa một quyết định vào spine:

> Nếu hai người (hoặc hai agent) build hai phần độc lập, họ **có thể chọn khác nhau và không khớp nhau**
> không? Chỉ ghi vào spine khi câu trả lời là _có_, lựa chọn không hiển nhiên, và là một đánh đổi thật.

Mỗi quyết định có dạng:

```markdown
### AD-3 — Mọi thay đổi trạng thái đơn hàng đi qua một hàm chuyển trạng thái thuần

- **Binds:** FR-2, FR-3, FR-5, src/features/orders
- **Prevents:** route handler hoặc UI tự gán `order.status = ...` và bỏ qua quy tắc chuyển
- **Rule:** chỉ `transitionOrder(order, to, actor, now)` trong `order-state-machine.ts` được đổi `status`;
  chuyển không hợp lệ ném `OrderError("INVALID_STATUS_TRANSITION", ...)`.
```

Quyết định mà code hiện có **đã chốt sẵn** được gắn `[ADOPTED]` (ví dụ kiến trúc feature-based, repository
pattern, server tính lại giá). ID `AD-n` không bao giờ đánh lại hay dùng lại - story ở bài 4.7 sẽ tham chiếu tới chúng.

| Mục của spine                 | Nội dung                                                               |
| ----------------------------- | ---------------------------------------------------------------------- |
| Design Paradigm               | Tên pattern + ánh xạ lớp → thư mục                                     |
| Invariants & Rules            | `AD-1..AD-n` (Binds / Prevents / Rule) + sơ đồ mermaid hướng phụ thuộc |
| Consistency Conventions       | Đặt tên, định dạng dữ liệu (id, ngày giờ, lỗi), state & cross-cutting  |
| Stack                         | Tên + **phiên bản đã pin**                                             |
| Structural Seed               | Sơ đồ mermaid, ERD, cây thư mục tối thiểu                              |
| Capability → Architecture Map | FR / capability nằm ở đâu, bị AD nào ràng buộc (chỉ khi dựng từ spec)  |
| Deferred                      | Quyết định cố ý để sau, kèm lý do                                      |

## Bước 1 - Gọi `/bmad-architecture` (20')

Mở phiên mới. Có thể gọi qua agent để có "giọng" kiến trúc sư: `/bmad-agent-architect` rồi chọn `CA`.

**Prompt**

```text
/bmad-architecture Tạo architecture spine cho tính năng trong
_bmad-output/planning-artifacts/prds/<thư mục>/prd.md (đọc cả addendum.md cùng thư mục) và UX trong
_bmad-output/planning-artifacts/ux-designs/<thư mục>/.
Đây là brownfield: điều tra code thật trước khi quyết định. Phê chuẩn các quy ước đã có thành [ADOPTED]
(feature-based src/features/<feature>, hàm thuần có test, OrderRepository interface, OrderError + handleRouteError,
server tính lại giá, Zod validate). Không thêm database hay dịch vụ ngoài; vẫn lưu file JSON trong storage/.
Phiên bản stack lấy từ package.json. Next.js 16: đọc node_modules/next/dist/docs/ khi cần (ví dụ proxy.ts).
```

Agent sẽ hỏi (bắt buộc, trước khi viết) **spine có phải sản phẩm duy nhất không, ai đọc, để làm gì** - trả
lời: _"Spine là đầu vào để chia story và để AI build (build-substrate), altitude feature. Không cần thêm tài
liệu khác."_

Mặc định skill chạy **Coaching path** (hỏi từng quyết định). Đây là phần đáng giá nhất của bài: hãy để
agent đưa phương án, **bạn** chọn. Các quyết định nên xuất hiện theo ý tưởng:

| Ý tưởng | Quyết định quan trọng (bạn nên thấy agent hỏi / đề xuất)                                                                                                                                                                                                                                                                                                                     |
| ------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A       | Máy trạng thái đặt ở đâu, là hàm thuần? · Lưu lịch sử trạng thái thế nào, migrate đơn cũ? · Tồn kho ghi được để ở đâu (`storage/inventory.json`?) và catalog đọc tồn kho thế nào? · Trừ kho lúc đặt hay lúc xác nhận? · Chống ghi đồng thời (hàng đợi/mutex trong tiến trình) · Bảo vệ `/admin` và `/api/admin/*` bằng gì (`src/proxy.ts`, cookie ký HMAC, biến môi trường)? |
| B       | Token truy cập đơn: sinh, lưu, so sánh (timing-safe) · Lưu "đơn của tôi" ở đâu · Rate limit tra cứu (giới hạn của bộ nhớ trong tiến trình) · Migrate đơn cũ không có token                                                                                                                                                                                                   |
| C       | Cấu hình sale ở đâu · Hàm giá theo thời gian inject `now()` · Múi giờ `Asia/Ho_Chi_Minh` · Đếm suất nguyên tử · Giá trong giỏ (snapshot) lệch giá sale thì xử lý ở đâu                                                                                                                                                                                                       |

Cú hích nếu agent bỏ sót:

```text
Repository hiện tại đọc-sửa-ghi toàn bộ orders.json và dùng chung một file orders.json.tmp. Nếu hai request
ghi cùng lúc thì sao? Có cần một AD cho việc tuần tự hóa thao tác ghi không?
```

## Bước 2 - Finalize: lint, reviewer, đối chiếu PRD (8')

Khi kết thúc, skill chạy:

1. **Đối chiếu input** - subagent đọc lại PRD/UX tìm yêu cầu "lặng lẽ" bị rơi.
2. **Reviewer gate**, mở đầu bằng **lint tự động** - `uv run .../scripts/lint_spine.py`: phát hiện
   `TBD/TODO`, ID `AD` trùng hoặc không tăng dần, AD thiếu Binds/Prevents/Rule, Stack chưa pin phiên bản.
   Sau đó là rubric + 2 reviewer mặc định:
   - _web verification_: phiên bản trong Stack có còn mới / có thật không.
   - _adversarial_: cố build **hai** phần cùng tuân thủ các AD nhưng **không khớp nhau** - nếu làm được,
     spine còn lỗ hổng.

Kết quả: `_bmad-output/planning-artifacts/architecture/architecture-<dự-án>-<ngày>/ARCHITECTURE-SPINE.md`
(+ `.memlog.md`, `reviews/`).

> 💡 Khi đóng, skill gợi ý bước tiếp theo là `bmad-spec` (con đường cho công việc cỡ một epic). Trong lab ta
> đi con đường dự án nhiều epic: **bỏ qua** gợi ý đó và sang bài 4.7.

## Bước 3 - Review (2')

- [ ] Có ít nhất 2 AD `[ADOPTED]` từ code hiện có và 3-6 AD mới.
- [ ] Mỗi AD có **Rule** kiểm chứng được khi đọc PR (không phải "nên viết code sạch").
- [ ] Stack khớp `package.json` (Next.js 16.4.2, React 19.3.0, Zod 4...), không có thư viện mới chưa giải thích.
- [ ] Các FR quan trọng của PRD đều được AD nào đó `Binds` tới. (Mục _Capability → Architecture Map_ chỉ có
      khi spine được dựng từ một spec của `bmad-spec`; thiếu mục này là bình thường.)
- [ ] _Deferred_ ghi rõ cái gì để sau (ví dụ "chuyển sang database thật").

## Bước 4 - Commit (1')

```bash
git add _bmad-output/planning-artifacts/architecture
git commit -m "docs(bmad): architecture spine"
```

✅ **Checkpoint:** spine có `status: final`; lint không còn lỗi; có AD về **ghi đồng thời / tính nhất quán
dữ liệu** (ý tưởng A, C) hoặc **kiểm soát truy cập** (ý tưởng B).
