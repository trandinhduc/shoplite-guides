# 5.3 - Sửa lỗi sau review và đóng vòng sprint

**Thời lượng:** 45 phút · **Kết quả:** mọi finding của story 1.1 được xử lý có lý do, mỗi lỗi được sửa kèm
test tái hiện; story chuyển `done`; (tùy chọn) bug bash đo độ nhạy của từng lớp review, retrospective cho epic 1.

## Lý thuyết nhanh: đọc finding như một reviewer có kinh nghiệm

AI reviewer **luôn** tìm ra thứ gì đó (Blind Hunter còn bị bắt phải tìm đủ N vấn đề). Việc của bạn không phải
là "Apply all" cho nhanh, mà là với mỗi finding trả lời được 4 câu:

1. **Có thật không?** Tái hiện được bằng một test hoặc một lệnh `curl` không?
2. **Do thay đổi này gây ra, hay có từ trước?** Có từ trước → `defer`, không sửa lẫn vào story.
3. **Sửa thế nào là đúng ý đồ?** Nếu có nhiều cách và phụ thuộc nghiệp vụ → đó là `decision_needed`, không
   để AI tự chọn.
4. **Test nào chứng minh đã sửa?** Mỗi patch phải đi kèm một test **fail trước khi sửa, pass sau khi sửa**.

## Bước 1 - Quyết định các finding `decision_needed` (5')

Quay lại phiên review của bài 5.2 (skill đang chờ ở bước _Resolve decision-needed findings_). Với mỗi mục,
đọc lại AC trong `epics.md` và PRD, rồi trả lời bằng **số** của phương án. Ví dụ:

```text
Finding: Khi xác nhận đơn mà một sản phẩm không đủ hàng - từ chối cả đơn hay xác nhận một phần?
1. Từ chối cả đơn với INSUFFICIENT_STOCK   2. Xác nhận phần đủ hàng   3. Defer
→ 1   (PRD: "đơn được xác nhận khi kho có đủ hàng" - không có khái niệm xác nhận một phần)
```

Chọn **Defer** thì skill hỏi một dòng lý do - ghi lý do thật, nó sẽ nằm trong `deferred-work.md`.

## Bước 2 - Xem từng patch rồi mới áp dụng (15')

Khi skill hỏi cách xử lý các finding `patch`, chọn **3. Walk through each patch**. Với mỗi patch, skill
hiện chi tiết, đoạn diff và cách sửa đề xuất. Áp 4 câu hỏi ở phần lý thuyết. Không đồng ý một patch thì nói
thẳng:

```text
Bỏ patch #4: CSRF không áp dụng vì API nhân viên xác thực bằng header Authorization, không dùng cookie.
Với các patch còn lại: mỗi patch phải kèm một unit test tái hiện lỗi (test fail trên code cũ).
```

Sau khi xem hết, chọn **1. Apply every patch** cho các patch đã đồng ý.

Kiểm chứng (terminal khác):

```bash
git diff --stat
npm run check                                              # phải pass sau khi áp patch

# Chứng minh test mới thật sự bắt được lỗi: tạm cất FILE NGUỒN đã sửa (giữ nguyên file test)
git stash push -- src/features/orders/order-state-machine.ts
npx vitest run src/features/orders                         # test mới phải FAIL
git stash pop
npx vitest run src/features/orders                         # PASS trở lại
```

(Thay đường dẫn bằng file nguồn mà patch đã sửa. Đừng `git stash` toàn bộ - sẽ cất luôn test mới.)

## Bước 3 - Cập nhật trạng thái và commit (5')

Skill tự quyết định trạng thái story:

| Kết quả review                                                       | Story →       |
| -------------------------------------------------------------------- | ------------- |
| Mọi `decision_needed` và `patch` đã xử lý, không còn `high`/`medium` | `done`        |
| Còn patch để lại làm action item, hoặc còn vấn đề chưa xử lý         | `in-progress` |

Ở câu hỏi _What would you like to do next?_ chọn **3. Done**.

> ⚠️ Phương án _"Start the next story - run `dev-story`"_ là tên skill cũ (v6.12.4 vẫn in ra). Story tiếp
> theo hãy dùng `/bmad-build` ở phiên mới như bài 5.1.

Code review **không tự commit** các patch:

```bash
grep -n "1-1-" _bmad-output/implementation-artifacts/sprint-status.yaml     # → done
git add -A
git commit -m "fix(orders): address code review findings for story 1.1"
```

Lặp lại bài 5.2 → 5.3 cho story 1.2 (và 1.3, 3.1 nếu đã build).

## Bước 4 (tùy chọn) - Kiểm chứng bản sửa bằng một lượt review nhỏ (5')

Phiên mới:

```text
/bmad-code-review commit range HEAD~1..HEAD, no spec
```

Chỉ review commit sửa lỗi, chế độ `no-spec` (3 lớp, không đồng bộ sprint status). Mong đợi:
`✅ Clean review — all layers passed.` hoặc chỉ còn finding `low`. Nếu bản sửa sinh lỗi mới - đó là lý do
phải review cả bản sửa.

## Bước 5 - Đóng epic và retrospective (5')

Khi mọi story của Epic 1 đã `done`:

- **Không skill nào của v6.12.4 tự đặt `epic-1: done`**. Sửa tay trong `sprint-status.yaml`, rồi kiểm tra:

  ```text
  /bmad-sprint-planning validate sprint status
  /bmad-sprint-planning show sprint status
  ```

- (Tùy chọn) retrospective cho epic - phiên mới:

  ```text
  /bmad-retrospective 1
  ```

  Skill gom bằng chứng từ git, chạy lens review trên diff của cả epic, đối chiếu với artifact, rồi kết luận
  `accepted` / `accepted-with-open-items` / `rejected` (story chưa xong → `rejected`). Kết quả:
  `_bmad-output/implementation-artifacts/epic-1-retro-<ngày>.md`; `epic-1-retrospective: done` và các
  action item được thêm vào `action_items` của `sprint-status.yaml`.

```bash
git add -A && git commit -m "docs(bmad): close epic 1 and retrospective"
```

## Bước 6 (tùy chọn, 15') - Bug bash: các lớp review bắt được bao nhiêu lỗi cài sẵn?

Code do AI viết có khi đã khá sạch, review không còn gì nhiều để bắt. Bài này **cố ý cài lỗi** để đo độ
nhạy của từng lớp. Cần đã build xong story 1.3 (API nhân viên); nếu chưa, bỏ lỗi số 2. Làm trên nhánh bỏ đi:

```bash
git checkout -b lab5-bugbash
```

Phiên Claude Code thường (không dùng skill BMAD):

```text
Cài đúng 4 lỗi sau vào code của Epic 1 (story 1.1-1.3). KHÔNG sửa hay xóa test hiện có, KHÔNG thêm comment
gợi ý, giữ code trông tự nhiên:
1. Cho phép chuyển từ một trạng thái cuối (cancelled hoặc delivered) sang trạng thái khác.
2. Khi biến môi trường khóa nhân viên chưa được đặt, API nhân viên vẫn cho qua (fail-open).
3. Bỏ await ở lệnh lưu đơn sau khi chuyển trạng thái (fire-and-forget).
4. Đổi một phép so sánh biên (> thành >= hoặc ngược lại) ở kiểm tra tồn kho hoặc độ dài ghi chú.
Commit với message "refactor: tidy order transition code" và KHÔNG cho tôi biết lỗi nằm ở dòng nào.
Riêng nhiệm vụ này bỏ qua quy tắc "npm run check phải pass" trong CLAUDE.md: không sửa lỗi nào, commit ngay
trong lượt này rồi mới dừng.
```

> ⚠️ Hook **quality-gate** (Stop) chặn agent dừng khi `src/` còn thay đổi chưa commit mà test đỏ - nên agent
> phải **commit trước khi dừng**. Nếu agent vẫn "lỡ tay" sửa lại lỗi, xem `git show HEAD` và cài lại cho đủ.

(Ý tưởng B/C: tự viết 4 lỗi tương tự cho code của bạn - một lỗi bảo mật, một lỗi biên, một lỗi bất đồng
bộ, một lỗi "lặng lẽ" ở trạng thái/dữ liệu.)

Rồi ở **phiên mới với model khác**:

```text
/bmad-code-review commit range HEAD~1..HEAD, spec _bmad-output/implementation-artifacts/spec-1-3-<slug>.md
```

Khi skill hỏi cách xử lý patch, chọn **2. Leave as action items** - ta chỉ đo, không sửa. Điền bảng:

| Lỗi cài            | Blind Hunter | Edge Case Hunter | Verification Gap | Acceptance Auditor | Triage giữ lại? |
| ------------------ | ------------ | ---------------- | ---------------- | ------------------ | --------------- |
| 1. Trạng thái cuối |              |                  |                  |                    |                 |
| 2. Fail-open       |              |                  |                  |                    |                 |
| 3. Thiếu await     |              |                  |                  |                    |                 |
| 4. Biên            |              |                  |                  |                    |                 |

Câu hỏi: commit message _"refactor: tidy..."_ có bị Edge Case Hunter bắt là **tuyên bố sai** (refactor mà
đổi hành vi) không? `npm run check` có bắt được lỗi nào không - nếu không, test hiện có còn thiếu gì?

Dọn dẹp (không merge nhánh này). Review đã ghi `### Review Findings` vào spec 1.3, đổi spec sang
`in-progress` và thêm mục vào `deferred-work.md` - các thay đổi này **chưa commit**, nếu không commit chúng
sẽ đi theo bạn sang `lab5-build` (cây git bẩn làm `/bmad-build` HALT, và `git add -A` sau đó sẽ commit nhầm
finding giả):

```bash
git add -A && git commit -m "chore: bug bash review (discard)"
git checkout lab5-build
git branch -D lab5-bugbash
git status                      # phải sạch
```

✅ **Checkpoint:** story 1.1 (và 1.2) ở `done`; mỗi patch đã áp dụng có test tái hiện; có ít nhất một
finding bạn **từ chối** kèm lý do; `epic-1` được đóng nếu đủ story; `npm run check` pass.
