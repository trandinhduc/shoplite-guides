# 5.2 - AI review code với `/bmad-code-review` (4 góc nhìn, model khác)

**Thời lượng:** 40 phút · **Kết quả:** story 1.1 được review bởi 4 reviewer độc lập chạy trên **model khác**
model đã viết code; bạn hiểu và chấm được từng finding.

## Lý thuyết nhanh

### Vì sao review lại khi `bmad-build` đã tự review?

`bmad-build` (bài 5.1) đã chạy 3 reviewer, nhưng chúng dùng **cùng model** với model viết code, nên dễ có
**cùng điểm mù**. BMAD khuyến nghị (ghi ngay trong `sprint-status.yaml`): _"Dev chuyển story sang `review`,
rồi chạy code-review (**ngữ cảnh mới, nên dùng LLM khác**)"_. `bmad-code-review` còn có lớp thứ 4 mà build
không có: **Acceptance Auditor** đối chiếu code với acceptance criteria.

### 4 góc nhìn

Mỗi lớp là một subagent chạy song song, **không thấy kết quả của nhau**:

| Lớp                       | Thấy gì                                                                 | Tìm gì                                                                                                                                      | Kiểu lỗi hay bắt                                              |
| ------------------------- | ----------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------- |
| 🙈 **Blind Hunter**       | **Chỉ diff**, không ngữ cảnh, không spec                                | Mọi thứ sai hoặc **thiếu**; bắt buộc tìm ít nhất N vấn đề (N = min(⌊√kB⌋ + 1, 10), kB = kích thước diff)                                    | Bảo mật, xử lý lỗi, code "trông không ổn"                     |
| 🔍 **Edge Case Hunter**   | Diff; **cuối cùng** mới đọc "claims" (commit message / mô tả)           | Mọi nhánh và biên chưa xử lý, lệch chữ ký hàm ở nơi gọi; kiểm tra phần **bị xóa**; kiểm tra lời tuyên bố trong commit                       | Biên `<`/`<=`, null, trạng thái lạ, "refactor" mà đổi hành vi |
| 🧪 **Verification Gap**   | Diff + **tìm và đọc test trong repo**                                   | Hồi quy không có test bắt; nơi lẽ ra phải dùng code mới mà chưa dùng (_missing adoption_); test không kiểm chứng gì (_broken verification_) | Test giả, code mới chưa được gọi                              |
| ✅ **Acceptance Auditor** | Diff + **spec của story** + tài liệu context (chỉ chạy ở chế độ `full`) | Vi phạm acceptance criteria, lệch ý đồ spec, hành vi được yêu cầu nhưng chưa làm                                                            | "Code chạy nhưng không đúng yêu cầu"                          |

Sau đó **triage** (bước 3 của skill) kiểm chứng lại từng finding bằng cách đọc code - **bỏ qua mức độ
nghiêm trọng reviewer tự gán** - rồi cho một verdict và xếp vào một nhóm:

| Verdict                   | Nhóm (bucket)       | Nghĩa                                                                                                         |
| ------------------------- | ------------------- | ------------------------------------------------------------------------------------------------------------- |
| `high` / `medium` / `low` | **patch**           | Lỗi thật, cách sửa rõ ràng, không cần hỏi người (`low` mà sửa làm code phức tạp hơn thì bị loại)              |
|                           | **decision_needed** | Lỗi thật nhưng sửa thế nào phụ thuộc ý đồ của bạn (chỉ có ở chế độ `full`)                                    |
|                           | **defer**           | Có thật nhưng **có từ trước** thay đổi này, hoặc sửa sẽ đụng `AGENTS.md`/`CLAUDE.md` → ghi `deferred-work.md` |
| `false`                   | _rejected_          | Báo nhầm (false positive)                                                                                     |
| `maybe-false`             | defer / rejected    | Chưa chắc; ghi lại cách để kiểm chứng                                                                         |

## Bước 1 - Chọn model review khác model đã build (8')

Xem model đang dùng: gõ `/model` trong Claude Code. Chọn **một** trong ba cách:

### Cách 1 (mọi người làm được) - đổi model Claude

`bmad-code-review` yêu cầu mọi subagent reviewer _"chạy cùng năng lực model với phiên hiện tại"_, nên
**đổi model của phiên = đổi model của cả 4 reviewer**.

```bash
claude --model sonnet        # nếu đã build bằng Opus
# hoặc
claude --model opus          # nếu đã build bằng Sonnet
```

(Hoặc gõ `/model` trong phiên mới và chọn.) Không nên dùng model quá nhỏ cho review - reviewer yếu sinh
nhiều finding nhầm.

### Cách 2 (khuyên dùng nếu có Codex CLI hoặc Gemini CLI) - thêm một lớp review chạy model hãng khác

Mỗi lớp review là một "công thức" (`instruction`) có thể thay. Thêm lớp thứ 5 chạy công cụ bên ngoài qua
bash, tạo `_bmad/custom/bmad-code-review.toml`:

```toml
# Lớp có id mới sẽ được THÊM vào 4 lớp mặc định (lớp trùng id sẽ bị thay thế).
[[workflow.review_layers]]
id = "other-llm-hunter"
name = "Blind Hunter (model hãng khác)"
instruction = """
Run this exact command with the Bash tool and return its full output verbatim as this layer's findings:
codex exec "You are a code reviewer. Read the unified diff at {diff_file}. List everything that is wrong or missing (bugs, edge cases, security, missing tests) as a Markdown list, each item with file:line. Do not modify any file."
"""
```

Dùng Gemini CLI thì thay dòng lệnh bằng `gemini -p "..."` với cùng nội dung. Cho phép lệnh trong
`.claude/settings.local.json` (`"Bash(codex exec *)"` hoặc `"Bash(gemini -p *)"`), rồi commit file toml.

### Cách 3 (nâng cao) - chạy cả `bmad-code-review` trong công cụ khác

Cài thêm skill cho Codex: chạy `npx bmad-method@6.12.4 install`, chọn **Modify BMAD Installation**, tích
thêm **Codex** ở bước _Integrate with_ (skill vào `.agents/skills/`). Mở `codex` trong `shoplite/` và gọi skill
`bmad-code-review`. Nếu công cụ không có subagent, BMAD sẽ ghi prompt của từng lớp ra
`_bmad-output/implementation-artifacts/` và nhờ bạn chạy mỗi prompt ở một phiên riêng rồi dán kết quả lại.

## Bước 2 - Chạy review story 1.1 (15')

Lấy thông tin diff của story (terminal thường):

```bash
grep baseline_commit _bmad-output/implementation-artifacts/spec-1-1-*.md   # commit trước khi code
git log --oneline -4                                                       # commit của story 1.1
```

Nếu story 1.1 đi đường **one-shot** ở bài 5.1, spec không có `baseline_commit`: dùng commit ngay trước commit
của story (`<commit story 1.1>~1`).

Mở **phiên mới** với model đã chọn ở Bước 1, gọi **không kèm tham số** để skill tự tìm story đang `review`
trong `sprint-status.yaml` (chỉ khi tìm theo cách này skill mới cập nhật trạng thái story ở cuối):

```text
/bmad-code-review
```

Skill liệt kê story đang `review` và hỏi **Review this story** / **Choose another target**. Trả lời **trong
cùng một tin nhắn** cả lựa chọn, nguồn diff và spec - nếu chỉ chọn "Review this story", skill sẽ tự đoán
nguồn diff (nhánh theo tên story, hoặc thay đổi chưa commit) và vì story đã được commit nên diff rỗng →
HALT _"nothing to review"_:

```text
Review this story (1.1), commit range <baseline_commit>..<commit story 1.1>,
spec _bmad-output/implementation-artifacts/spec-1-1-<slug>.md
```

Có spec → chế độ **full** (đủ 4 lớp). Ở **CHECKPOINT** (thống kê diff, chế độ, tài liệu đã nạp), kiểm tra số
file/dòng có khớp `git show --stat <commit story 1.1>` không rồi cho chạy tiếp.

> ⚠️ Hai điều kiện để cuối buổi review story tự chuyển `done` trong `sprint-status.yaml`: skill phải **tự tìm**
> story từ sprint status (gọi không tham số như trên - nếu gọi kèm đường dẫn spec hoặc commit ngay từ đầu,
> biến `story_key` không được đặt) **và** phải có spec. Chọn "Continue without a spec" thì Acceptance
> Auditor bị bỏ qua (chế độ `no-spec`) và trạng thái không được cập nhật.

Skill thông báo lớp nào bị bỏ qua, chạy các lớp song song, triage, rồi in dòng tổng kết:

```text
Code review complete. <D> decision-needed, <P> patch, <W> defer, <R> rejected.
```

và ghi vào spec một mục:

```markdown
### Review Findings

- [ ] [Review][Decision] Xác nhận thiếu hàng: từ chối cả đơn hay xác nhận một phần? — AC 3.1 không nói rõ đơn nhiều sản phẩm
- [ ] [Review][Patch] Chuyển trạng thái trùng (confirmed → confirmed) ghi lịch sử 2 lần [src/features/orders/order-state-machine.ts:31]
- [x] [Review][Defer] File tạm orders.json.tmp dùng chung giữa các lần ghi — deferred: có từ trước story này
```

Mục _defer_ đồng thời được chép vào `_bmad-output/implementation-artifacts/deferred-work.md`.

**Dừng ở đây** - chưa chọn cách sửa. Bài 5.3 sẽ xử lý trong chính phiên này.

## Bước 3 - Chấm điểm reviewer (15')

Điền bảng (nộp cùng bài). Mỗi dòng là một finding sau triage:

| #   | Lớp phát hiện | Mô tả ngắn | Verdict (`high/medium/low/false`) | Bucket | Bạn đồng ý? | Nếu không, vì sao |
| --- | ------------- | ---------- | --------------------------------- | ------ | ----------- | ----------------- |
| 1   |               |            |                                   |        |             |                   |

Rồi trả lời:

1. Lớp nào tìm được nhiều finding **thật** nhất? Lớp nào báo nhầm nhiều nhất?
2. Có finding nào **chỉ** Acceptance Auditor bắt được (vì cần đọc spec)? Có finding nào **chỉ** Blind Hunter
   bắt được (vì không bị spec "dẫn dắt")?
3. So với `## Review Triage Log` của `bmad-build` ở bài 5.1: model khác tìm ra điều gì mà model build bỏ sót?
4. Nếu dùng Cách 2: lớp model hãng khác trùng bao nhiêu % với 4 lớp Claude?

Xem ví dụ các finding điển hình và cách sửa: [reference/review-findings-example.md](reference/review-findings-example.md).

✅ **Checkpoint:** review chạy ở chế độ **full** với đủ 4 lớp (hoặc 5 với Cách 2) trên model khác model build;
spec story 1.1 có mục `### Review Findings`; bảng chấm điểm có ít nhất 5 dòng.
