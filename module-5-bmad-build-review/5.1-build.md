# 5.1 - Implement story với `/bmad-build`

**Thời lượng:** 60 phút · **Kết quả:** story 1.1 và 1.2 của Sprint 1 được code, test, tự review và commit;
`sprint-status.yaml` chuyển các story sang `review`.

## Lý thuyết nhanh: một story đi qua `bmad-build` thế nào

`bmad-build` là cách **chính thức** BMAD v6.12 dùng để viết code (thay cho `bmad-quick-dev`,
`bmad-create-story` + `bmad-dev-story` của các bản cũ; `bmad-build-auto` là biến thể chạy không cần người,
dùng cho vòng lặp tự động - không dùng trong lab). Nó tự quyết định cần bao nhiêu "nghi thức" **sau khi**
điều tra code:

```text
step-01 Clarify & route ─► step-02 Plan ─────────────► CHECKPOINT 1 ─► step-03 Implement ─► step-04 Review ─► step-05 Present
 đọc story, gom epic        điều tra code bằng          bạn duyệt        subagent MỚI          3 reviewer         spec done,
 context, kiểm tra cây      subagent; viết spec;        spec             (không mang hội        độc lập +          story → review,
 git sạch                   hỏi Open Questions                           thoại cũ) code + test  triage, sửa        commit local

      └── thay đổi nhỏ, không mơ hồ, không có gì "không đảo ngược được" ─► step-oneshot (spec 2 mục, làm luôn)
```

> 💡 Nếu agent chọn **one-shot**: không có Checkpoint 1, phiên chính tự code (không qua subagent), không
> có Matrix Test Audit, chỉ 1 lớp review (`blind-hunter`), spec không có `baseline_commit`. Story 1.1 (máy
> trạng thái, nhiều trường hợp biên) thường sẽ **không** đi one-shot - nếu có, hãy hỏi agent vì sao.

Điểm khác với Spec Kit / OpenSpec:

| Điểm           | `bmad-build`                                                                                                                                                                  |
| -------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Spec của story | `_bmad-output/implementation-artifacts/spec-1-1-<slug>.md` - phần `<frozen-after-approval>` (Intent, Boundaries, I/O & Edge-Case Matrix) **chỉ người được sửa** sau khi duyệt |
| Người code     | Một **subagent không có ngữ cảnh hội thoại**, chỉ đọc spec + các file trong `context:` của spec                                                                               |
| Kiểm test      | _Matrix Test Audit_: mỗi dòng trong I/O & Edge-Case Matrix phải có test đã chạy và pass                                                                                       |
| Tự review      | 3 lớp: `blind-hunter` (chỉ thấy diff), `edge-case-hunter` (diff + đối chiếu claim), `verification-gap` (diff + tìm trong repo)                                                |
| Kết quả review | `patch` (tự sửa) · `defer` (ghi `deferred-work.md`) · `bad_spec` (sửa spec, code lại) · `intent_gap` (hỏi lại bạn)                                                            |
| Kết thúc       | Commit **local**, không bao giờ push; story → `review` (chưa `done` - `done` là việc của bài 5.2)                                                                             |

## Bước 1 - Chuẩn bị nhánh và kiểm tra trạng thái (5')

Module 5 **kế thừa** Module 4: tách nhánh từ `lab4-bmad` để toàn bộ diff của nhánh mới chỉ là code.

```bash
cd shoplite
git checkout lab4-bmad && git status        # phải sạch - bmad-build HALT nếu cây git bẩn
git checkout -b lab5-build
```

Mở phiên Claude Code mới:

```text
/bmad-sprint-planning show sprint status
```

Mong đợi: 4 story `ready-for-dev`, đề xuất tiếp theo là `bmad-build` cho story `1-1-...`.

(Tùy chọn - khuyên làm) cho các skill ship luôn nạp quy tắc dự án. Tạo `_bmad/custom/bmad-build.toml`:

```toml
[workflow]
persistent_facts = [
  "file:{project-root}/AGENTS.md",
  "Mọi thay đổi nghiệp vụ phải có unit test cho trường hợp biên; npm run check phải pass.",
]
```

```bash
git add _bmad/custom/bmad-build.toml
git commit -m "chore(bmad): load AGENTS.md as persistent fact for bmad-build"   # cây git phải sạch trước khi build
```

> 💡 `persistent_facts` chỉ nạp vào **phiên điều phối** của `bmad-build` (file override chỉ áp dụng cho
> skill trùng tên; muốn cho `bmad-code-review` thì tạo `bmad-code-review.toml` tương tự). Subagent viết
> code không thấy chúng - nó chỉ đọc spec và các file liệt kê trong `context:` của spec. Vì vậy ở Checkpoint
> 1 bạn phải kiểm tra `context:`.

Ví dụ trong bài dùng ý tưởng A (story 1.1 máy trạng thái, 1.2 lịch sử). Với ý tưởng B/C, thay bằng các
story trong Sprint 1 của nhóm bạn - các bước giống hệt.

## Bước 2 - Build story 1.1 (25')

Mở phiên mới (`/clear`). Có thể gọi qua Dev: `/bmad-agent-dev` → `BD`.

**Prompt**

```text
/bmad-build story 1.1 trong _bmad-output/planning-artifacts/epics.md
(sprint-status: _bmad-output/implementation-artifacts/sprint-status.yaml).
Tài liệu nguồn của epic: PRD _bmad-output/planning-artifacts/prds/<thư mục>/prd.md,
spine _bmad-output/planning-artifacts/architecture/<thư mục>/ARCHITECTURE-SPINE.md,
UX _bmad-output/planning-artifacts/ux-designs/<thư mục>/.
```

Những gì sẽ xảy ra và việc của bạn:

| Lúc              | Agent làm                                                                                           | Bạn làm                                                                                                                  |
| ---------------- | --------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| Epic context     | Gom thông tin epic 1 từ PRD/spine/UX vào `implementation-artifacts/epic-1-context.md`               | Mở file: mục _Technical Decisions_ có nêu đúng các quyết định kiến trúc liên quan không? (file cố ý không trích mã AD-n) |
| Kiểm tra git     | Cây git bẩn (kể cả do `epic-1-context.md` vừa tạo) → HALT và hỏi                                    | Trả lời _"Tiếp tục, đó là file context của BMAD"_ (file sẽ vào commit của story)                                         |
| Plan             | Subagent điều tra code (`order-service.ts`, `types.ts`, test hiện có...), viết `spec-1-1-<slug>.md` | Chờ                                                                                                                      |
| Open Questions   | Liệt kê **tất cả** câu hỏi cùng lúc, đánh số, kèm phương án                                         | Trả lời theo số; câu trả lời được ghi vào phần _frozen_                                                                  |
| **CHECKPOINT 1** | **Approve and continue** / **Approve and stop** / **Review spec**                                   | Đọc spec theo checklist bên dưới, rồi chọn                                                                               |
| Implement        | Subagent mới code + test theo spec; phiên chính đối chiếu diff và đánh dấu task `[x]`               | Theo dõi `git diff --stat` ở terminal khác                                                                               |
| Review           | 3 reviewer chạy song song → triage → patch                                                          | Trả lời nếu bị hỏi (intent gap, quyết định)                                                                              |
| Present          | Spec `done`, story → `review`, **commit local**                                                     | Hộp thoại xin quyền `git commit` (rule `ask` của Module 1) - đọc message rồi đồng ý                                      |

**Checklist trước khi Approve ở Checkpoint 1:**

- [ ] _I/O & Edge-Case Matrix_ có đủ trường hợp biên của AC (với story 1.1: cả ma trận chuyển trạng thái,
      trạng thái cuối `delivered`/`cancelled`, khách hủy đơn `confirmed`).
- [ ] _Boundaries & Constraints_ có mục **Never** hợp lý (ví dụ "Never sửa trực tiếp `order.status` ngoài
      `transitionOrder`", "Never đổi hành vi `PATCH /api/orders/:id` của khách").
- [ ] _Code Map_ trỏ đúng file theo `AGENTS.md` (code mới trong `src/features/orders/`, test đặt cạnh file).
- [ ] Frontmatter `context:` có `AGENTS.md` và spine - nếu thiếu, chọn **Review spec** hoặc nói
      _"Thêm AGENTS.md và ARCHITECTURE-SPINE.md vào context của spec"_.
- [ ] Spec không quá dài (> 1600 token agent sẽ đề nghị **Split**).

> 💡 **Approve and stop** để spec ở `ready-for-dev` - phiên `bmad-build` sau đọc spec và đi thẳng vào
> implement. Dùng khi spec dài, muốn implement ở phiên sạch.

> ⚠️ Hook **quality-gate** (Stop) của Module 1 chạy `npm test` mỗi khi agent dừng mà `src/` có thay đổi. Nếu
> agent dừng ở một checkpoint khi test đang đỏ, hook sẽ buộc agent làm tiếp - đó là hook đang làm đúng việc.
> Hook **format-file** tự chạy Prettier sau mỗi lần sửa nên diff có thể khác code subagent viết ra chút ít.

## Bước 5 (nhóm nhanh / về nhà) - Story 1.3 và 3.1

Làm tương tự, **mỗi story một phiên mới**. Lưu ý riêng:

- **Story 1.3** (API cho nhân viên, ý tưởng A) cần biến môi trường. Tạo `.env.local` bằng tay (agent bị
  chặn sửa `.env*` bởi hook Module 1 - đúng ý đồ):

  ```bash
  echo "STAFF_API_KEY=dev-staff-key-123" >> .env.local     # >> để không ghi đè file đang có
  npm run dev
  curl -i -X PATCH http://localhost:3000/api/admin/orders/<mã đơn> \
    -H "Authorization: Bearer dev-staff-key-123" -H "Content-Type: application/json" \
    -d '{"status":"confirmed","note":"Đã kiểm hàng"}'
  ```

  (chạy `curl` trong terminal của bạn - Module 1 chặn `curl` cho agent). Windows: dùng Git Bash, hoặc
  PowerShell với `Add-Content .env.local "STAFF_API_KEY=dev-staff-key-123" -Encoding utf8` và `curl.exe`
  (trong PowerShell, `echo ... >` ghi file UTF-16 và `curl` là alias của `Invoke-WebRequest`). Không dán giá
  trị bí mật thật vào prompt; hook `scan-prompt` sẽ chặn chuỗi dạng `password=...`, `secret: ...`.

- **Story 3.1** (tồn kho) là story **rủi ro nhất** của sprint (ghi đồng thời, số lượng âm, hoàn kho sai) -
  rất đáng để làm trước bài 5.2.

`in-progress`; mỗi story có một commit riêng; `npm run check` pass; spec của mỗi story có `status: done` và
