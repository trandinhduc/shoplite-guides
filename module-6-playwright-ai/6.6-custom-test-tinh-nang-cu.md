# 6.6 - Custom test cho tính năng bạn đã làm (Module 2, 3 hoặc 5) bằng AI

**Thời lượng:** 40 phút · **Kết quả:** nhánh tính năng của bạn có bộ E2E hồi quy của bài 6.4 chạy xanh, cộng
**ít nhất 3 test custom** cho chính tính năng đó: có **custom fixture**, dùng **ít nhất 2 kỹ thuật** của
Playwright ngoài bấm và gõ, mang tag tiêu chí, và **đỏ khi cài lỗi** vào tính năng.

> 🎬 **Gợi ý demo (5'):** mở [reference/feature-tests/ma-giam-gia.spec.ts](reference/feature-tests/ma-giam-gia.spec.ts).
> Chỉ ba chỗ: vòng `for` sinh 5 test từ bảng 5 mã của bài 2.5; `page.route` giả server trả _"Mã giảm giá đã
> hết hạn"_ đúng lúc bấm đặt hàng (chờ thật tới 23:59:59 ngày hết hạn thì không ai làm nổi); và `request.post`
> gửi `discount` giả để thử gian lận. Hỏi lớp: _ba thứ này codegen có ghi lại được không?_

## Lý thuyết nhanh

### "Custom" gồm ba tầng

1. **Custom fixture** (`test.extend`): việc chuẩn bị riêng của tính năng, viết một lần, dùng mọi test -
   `coupon.apply("SHOPLITE10")`, một API context mang khóa nhân viên, dữ liệu yêu thích ghi sẵn.
2. **Custom test**: kịch bản mà bấm chuột không dựng được - giả lập server, gọi API thẳng, hai tab, chuẩn bị
   dữ liệu trước khi trang chạy, sinh nhiều test từ một bảng dữ liệu.
3. **AI viết theo đơn đặt hàng của bạn**: **bạn** chọn tiêu chí và kỹ thuật; AI (Claude Code, dùng MCP
   `playwright-test` để thử locator trên trình duyệt thật) viết; **bạn** duyệt bằng checklist.

### Chọn kỹ thuật theo tính năng

| Tính năng                             | Nhánh           | Tiêu chí lấy ở đâu                                                                                  | Khó kiểm bằng bấm chuột                                                                        | Kỹ thuật Playwright gợi ý                                                                                                          |
| ------------------------------------- | --------------- | --------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| **Mã giảm giá** (Module 2)            | `lab2-speckit`  | `specs/001-<tên>/spec.md` + bảng 9 ca thủ công ở bài 2.5                                             | Mã hết hạn đúng lúc đặt hàng; gửi `discount` giả qua API; 5 mã × nhiều giỏ                     | `page.route` + `route.fulfill`, fixture `request`, vòng `for` (data-driven), `page.reload`, `test.step`                            |
| **Danh sách yêu thích** (Module 3)    | `lab3-openspec` | `openspec/specs/wishlist/spec.md`                                                                   | Đồng bộ giữa 2 tab; giữ sau khi tải lại; giới hạn 50 (catalog chỉ có 16 sản phẩm); screen reader | `context.newPage`, `page.reload`, `page.addInitScript`, `toHaveAttribute("aria-pressed")`, `keyboard.press`                         |
| **ShopLite Ops** (Module 4-5, ý tưởng A) | `lab5-build` | `_bmad-output/planning-artifacts/epics.md` (AC story 1.1-1.3) + spec của story                      | Ma trận chuyển trạng thái; API nhân viên có khóa; khách thấy trạng thái nhân viên vừa đổi       | `playwright.request.newContext({ extraHTTPHeaders })`, data-driven, `test.skip(điều kiện, lý do)`, kết hợp API + giao diện         |

Ý tưởng B/C của Module 4-5: tự chọn theo cùng cách (B: token truy cập đơn → `request` với header/cookie,
hai `context` khác nhau = hai khách; C: giờ vàng → `page.clock` cho phía trình duyệt, nhưng nhớ giờ **server**
không đổi theo).

## Bước 1 - Gộp bộ test vào nhánh tính năng, chạy hồi quy (7')

Ví dụ với mã giảm giá (đổi tên nhánh theo tính năng của bạn):

```bash
git checkout lab2-speckit && git status            # phải sạch
git checkout -b lab6-coupon
git merge lab6-e2e                                  # mang theo config, agent, fixtures, tiêu chí, 11 test
npx playwright test --reporter=line                 # bộ hồi quy: tính năng mới có làm hỏng luồng cũ không?
```

| Tính năng           | Nhánh nguồn     | Nhánh mới         |
| ------------------- | --------------- | ----------------- |
| Mã giảm giá         | `lab2-speckit`  | `lab6-coupon`     |
| Danh sách yêu thích | `lab3-openspec` | `lab6-wishlist`   |
| ShopLite Ops        | `lab5-build`    | `lab6-ops`        |

> ⚠️ Xung đột khi merge: nhánh `lab2-speckit` có thể đã sửa `e2e/shopping-flow.spec.ts` (task thêm kịch bản
> `SHOPLITE10` ở bài 2.4). `lab6-e2e` không sửa file này nên thường merge sạch. Nếu `.claude/settings.json`
> xung đột, **giữ cả hai** phía (quyền của Module 6 nằm trong `settings.local.json`, không commit).
>
> 💡 Spec Kit cũng dùng thư mục `specs/` (`specs/001-.../`). Kế hoạch Playwright nằm cạnh, không đụng nhau.

**Nếu bộ hồi quy đỏ** - đọc màu đỏ như bài 6.5 trước khi sửa gì:

- Mã giảm giá thêm dòng _Giảm giá_ vào tóm tắt → `getByText("Miễn phí", { exact: true })` vẫn đúng; nhưng
  nếu bạn đổi nhãn _Tổng thanh toán_ hay `data-testid` → test sai, sửa locator (healer làm được).
- Ops (story 3.1) **trừ tồn kho thật** → _Giá đỡ laptop nhôm_ có thể không còn 3 → GH-2 đỏ vì **dữ liệu**
  đổi, không phải vì app sai. Cách sửa đúng: một fixture chuẩn bị tồn kho (ghi `storage/inventory.json` hoặc
  gọi API nhân viên) - đây là bài tập custom fixture rất tốt cho nhóm Ops.

## Bước 2 - Viết tiêu chí cho tính năng (8')

Thêm một mục mới vào `specs/tieu-chi.md`, mã theo tính năng: `MG-1..` (mã giảm giá), `YT-1..` (yêu thích),
`VH-1..` (vận hành). 3-5 tiêu chí, **lấy từ spec của tính năng** (cột "Tiêu chí lấy ở đâu" ở trên), không lấy
từ code.

**Prompt**

```text
Đọc <đường dẫn spec của tính năng> và specs/tieu-chi.md (để theo cùng cách viết).
Thêm vào specs/tieu-chi.md mục "Luồng C - <tên tính năng>" với 3-5 tiêu chí mã <MG|YT|VH>-1, -2...
Ưu tiên tiêu chí mà bấm chuột thường KHÔNG kiểm được: phụ thuộc thời gian, gian lận qua API, nhiều tab,
giới hạn số lượng lớn, phân quyền. Mỗi tiêu chí ghi nguồn (mục nào trong spec) và dữ liệu mẫu cụ thể.
Chỉ sửa specs/tieu-chi.md.
```

Duyệt như bài 6.1 (5 câu hỏi), rồi commit.

## Bước 3 - Cho AI viết custom fixture và test (15')

Hai cách, chọn một:

**Cách 1 - Đơn đặt hàng trực tiếp (khuyên dùng cho custom test).**

```text
Viết test E2E cho các tiêu chí <MG-1..MG-5> trong specs/tieu-chi.md, đặt trong e2e/<ma-giam-gia>/.

1. Trước hết tạo custom fixture bằng test.extend, dựng trên e2e/fixtures.ts có sẵn (giữ fixture shop và
   createPendingOrder). Fixture mới: <coupon.apply(code)>. Chỉ một file dùng thì khai báo ngay đầu file
   test; nhiều file dùng thì tách ra e2e/<ma-giam-gia>/fixtures.ts.
   Tham số thứ hai của fixture đặt tên provide (ESLint của Next nhầm `use` là React hook).
2. Mỗi tiêu chí ít nhất 1 test, tag { tag: "@MG-1" }...
3. Dùng các kỹ thuật sau ở đúng tiêu chí cần chúng:
   - <page.route + route.fulfill> để giả lập <server từ chối mã lúc đặt hàng>
   - <fixture request> để <gửi discount/total giả lên POST /api/orders>
   - <vòng for trên một bảng dữ liệu> cho <5 mã trong bảng thủ công của bài 2.5>
4. Trước khi ghi file, mở trang thật bằng các tool của MCP playwright-test để kiểm locator và câu chữ.
5. Locator theo .claude/rules/testing.md: getByRole/getByLabel trước, getByTestId sau cùng. Không
   waitForTimeout, không force, không networkidle. Kỳ vọng lấy từ tiêu chí, không tính lại bằng hàm của app.
Chạy npx playwright test e2e/<ma-giam-gia> --repeat-each=3 và npm run check, sửa tới khi xanh.
```

(Thay phần trong `< >` theo bảng "Chọn kỹ thuật" ở trên.)

**Cách 2 - Qua ba agent.** Planner (tiêu chí MG, ghi kế hoạch `specs/ma-giam-gia.plan.md`) → Bảng A →
generator. Hợp với phần **giao diện** của tính năng; phần giả lập mạng và API thì generator ít khi tự nghĩ
ra - bạn thường phải nhắn thêm như Cách 1.

Đối chiếu ý tưởng (không phải đáp án chạy được - nhãn và route phụ thuộc code của bạn):

- Mã giảm giá: [reference/feature-tests/ma-giam-gia.spec.ts](reference/feature-tests/ma-giam-gia.spec.ts)
- Danh sách yêu thích: [reference/feature-tests/yeu-thich.spec.ts](reference/feature-tests/yeu-thich.spec.ts)
- ShopLite Ops: [reference/feature-tests/van-hanh-don.spec.ts](reference/feature-tests/van-hanh-don.spec.ts)
  (cần `STAFF_API_KEY` ở **cả** dev server lẫn tiến trình test - xem đầu file)

> ⚠️ Ba lời khuyên khi đọc test AI viết cho tính năng của chính bạn:
>
> - `page.clock` chỉ đổi giờ **trình duyệt**. Nếu server kiểm hạn mã giảm giá, đổi giờ trình duyệt không làm
>   mã hết hạn - dùng `page.route` để giả câu trả lời của server, hoặc unit test với `now` cố định.
> - `page.route` thay server **trong test đó**: test xanh chỉ chứng minh _giao diện xử lý đúng câu trả lời
>   lỗi_, không chứng minh server trả lỗi đúng. Cần thêm một test API (`request`) cho phía server.
> - Giới hạn 50 sản phẩm yêu thích mà catalog chỉ có 16: nếu store của bạn bỏ id không có trong catalog, test
>   ghi sẵn 50 id giả sẽ không kiểm được gì. Khi đó giới hạn là việc của unit test - ghi vào mục
>   "Cố ý không đưa vào E2E" và nói rõ vì sao.

## Bước 4 - Chứng minh test bắt được lỗi (7')

Một test custom xanh chưa nói lên gì. Cài một lỗi nhỏ vào **tính năng** (không phải vào test) - như bug bash
của bài 5.3, trên nhánh bỏ đi:

```bash
git checkout -b lab6-mutation
```

**Prompt** (phiên Claude Code thường)

```text
Cài đúng 1 lỗi vào code của tính năng <mã giảm giá>, KHÔNG sửa e2e/ hay test, không thêm comment gợi ý.
Chọn một trong: so sánh mã phân biệt hoa thường; bỏ kiểm tra giá trị đơn tối thiểu ở server; đổi > thành >=
ở mức giảm tối đa. Commit với message "refactor: tidy coupon code" và KHÔNG cho tôi biết lỗi nằm ở đâu.
Riêng nhiệm vụ này bỏ qua quy tắc "npm run check phải pass" trong CLAUDE.md.
```

(Ops: "cho phép chuyển từ cancelled sang trạng thái khác" hoặc "API nhân viên cho qua khi chưa đặt khóa".
Wishlist: "bỏ lắng nghe sự kiện storage" hoặc "không lưu vào localStorage".)

```bash
npx playwright test e2e/<thư-mục-tính-năng> --reporter=line    # ít nhất 1 test custom phải ĐỎ
git checkout lab6-coupon && git branch -D lab6-mutation
```

Không test nào đỏ? Bộ test custom chưa đủ - tiêu chí bị lỗi vi phạm chưa có test, hoặc test kiểm sai thứ.
Bổ sung rồi thử lại. Điền cột thứ hai của **Bảng D**.

## Bước 5 - Commit và nộp bài (3')

```bash
npx prettier --write e2e specs

npx playwright test --repeat-each=3 --reporter=dot
git add e2e specs
git commit -m "test(e2e): custom tests for <coupon> with fixture, route mocking and API checks"
```

✅ **Checkpoint:** trên nhánh tính năng, bộ 11 test của bài 6.4 xanh; ≥ 3 test custom mang tag `MG/YT/VH`,
có custom fixture, dùng ≥ 2 kỹ thuật trong bảng "Chọn kỹ thuật"; cả bộ xanh 3 lần liên tiếp; Bước 4 làm đỏ
được ít nhất 1 test custom; `npm run check` pass.

## Tổng kết: AI trong vòng đời phần mềm qua 6 module

| Module | AI làm                                                  | Người giữ                                                    |
| ------ | ------------------------------------------------------- | ------------------------------------------------------------ |
| 1      | Làm việc trong repo theo context file, quyền, hook       | Luật chơi: được làm gì, bị chặn gì                           |
| 2-3    | Viết spec, kế hoạch, code theo spec                      | Câu trả lời cho `clarify`, duyệt proposal                    |
| 4-5    | Brainstorm, PRD, kiến trúc, story, code, review 4 lớp    | Phần _frozen_ của spec, `decision_needed`, quyết định defer  |
| 6      | Lập kế hoạch test, sinh test, sửa test hỏng              | **Bộ tiêu chí**, Bảng A, Bảng B, quyết định "test sai hay app sai" |
