# 6.3 - Thực hành các lệnh có sẵn của Playwright

**Thời lượng:** 30 phút · **Kết quả:** chạy, lọc, xem, gỡ lỗi, chạy lặp và đọc trace bằng các lệnh có sẵn
của Playwright; tự tay làm lộ một test **chập chờn do app**; biết các hàm sẽ dùng ở bài 6.4 - 6.6.

> 🎬 **Gợi ý demo (5'):** `npx playwright test --ui` - bấm một test, kéo thanh thời gian để thấy DOM từng
> bước, bật _Pick locator_ chỉ vào nút _Thêm vào giỏ_. Rồi chạy Bài tập 5 trên máy giảng viên: lớp thấy
> test đỏ ngẫu nhiên dù **không ai sửa test**.

Tất cả lệnh chạy trong `shoplite/`, dev server đang chạy ở terminal khác (`npm run dev`). Lúc này bạn có
5 test: `seed`, 2 test GH-1, 2 test mẫu trong `shopping-flow.spec.ts`. Thế là đủ để luyện.

## Bảng lệnh (Playwright 1.64)

| Việc                            | Lệnh                                                                         |
| ------------------------------- | ---------------------------------------------------------------------------- |
| Chạy tất cả                     | `npx playwright test` (hoặc `npm run test:e2e`)                              |
| Một thư mục / một file          | `npx playwright test e2e/gio-hang`                                           |
| Đúng một test theo dòng         | `npx playwright test e2e/gio-hang/them-san-pham.spec.ts:31`                  |
| Theo tên                        | `npx playwright test -g "hết hàng"`                                          |
| Theo tag tiêu chí               | `npx playwright test --grep @GH-1` · `--grep "@GH\|@DH"` · `--grep-invert @DH` |
| Liệt kê, không chạy             | `npx playwright test --list`                                                 |
| Thấy trình duyệt                | `npx playwright test --headed`                                               |
| Giao diện UI (xem, chạy lại)    | `npx playwright test --ui`                                                   |
| Gỡ lỗi từng bước                | `npx playwright test --debug` (hoặc đặt `await page.pause()` trong test)     |
| Ghi thao tác thành code         | `npx playwright codegen <url>`                                               |
| Báo cáo HTML                    | `npx playwright show-report`                                                 |
| Chạy lặp để lộ test chập chờn   | `npx playwright test --repeat-each=3`                                        |
| Chạy lại khi đỏ / cấm chập chờn | `--retries=2` · `--fail-on-flaky-tests`                                      |
| Chỉ chạy lại test vừa đỏ        | `npx playwright test --last-failed`                                          |
| Dừng ở test đỏ đầu tiên         | `npx playwright test -x`                                                     |
| Chỉ file test đã đổi (git)      | `npx playwright test --only-changed` · `--only-changed=main`                 |
| Số tiến trình chạy song song    | `--workers=4`                                                                |
| Kiểu in kết quả                 | `--reporter=dot` · `line` · `list`                                           |
| Xem trace bằng giao diện        | `npx playwright show-trace test-results/<thư-mục>/trace.zip`                 |
| Đọc trace bằng dòng lệnh        | `npx playwright trace open <trace.zip>` rồi `actions`, `action <số>`, `requests`, `errors`, `snapshot <số> --phase after snapshot`, `close` |

## Bài tập 1 - Chạy và lọc (5')

```bash
npx playwright test --list                     # bao nhiêu test? tag hiện ở cuối tên
npx playwright test --grep @GH-1 --reporter=line
npx playwright test e2e/gio-hang/them-san-pham.spec.ts:31     # số dòng của test thứ hai trong file của bạn
npx playwright test -g "lọc theo danh mục" --headed
```

Câu hỏi: `--grep @GH` chạy những test nào? Nếu sau này có `@GH-10`, `--grep @GH-1` có chạy nhầm nó không?
(Có - `--grep` là biểu thức chính quy. Dùng `--grep "@GH-1\b"` hoặc `--grep "@GH-1$"`.)

## Bài tập 2 - UI mode và báo cáo (7')

```bash
npx playwright test --ui
```

Trong UI mode:

1. Gõ `@GH-1` vào ô lọc → chỉ còn 2 test. Bấm ▶ chạy.
2. Bấm vào test _"sản phẩm hết hàng..."_, kéo thanh thời gian: mỗi bước có ảnh DOM **trước / sau**.
3. Bấm biểu tượng **Pick locator**, chỉ vào nút _Thêm vào giỏ_ trong khối mua → UI gợi ý locator.
4. Bật **watch** (biểu tượng con mắt) cho file, sửa một chữ trong test → test tự chạy lại.

Đóng UI, chạy cả bộ rồi mở báo cáo:

```bash
npx playwright test
npx playwright show-report
```

Ô tìm kiếm của báo cáo nhận `@GH-1` (theo tag), `s:failed` (theo trạng thái) hoặc chữ bất kỳ trong tên test / tên file.

## Bài tập 3 - Gỡ lỗi một test đỏ (7')

Cố ý làm đỏ: trong `e2e/gio-hang/them-san-pham.spec.ts` đổi `"Giỏ hàng (3 sản phẩm)"` thành
`"Giỏ hàng (4 sản phẩm)"`.

```bash
npx playwright test --grep @GH-1 -x
```

1. Đọc thông báo lỗi: locator nào, mong gì, nhận gì, đợi bao lâu.
2. Mở bằng chứng trong `test-results/<tên test>/`: `test-failed-1.png`, `video.webm`, `trace.zip`,
   `error-context.md` (Playwright 1.64 tự viết sẵn file này để **dán cho AI**: tên test, lỗi, cây accessibility
   lúc hỏng).
3. Xem trace bằng giao diện: `npx playwright show-trace test-results/<thư-mục>/trace.zip`.
4. Đọc trace bằng dòng lệnh (cách agent đọc ở bài 6.5):

   ```bash
   npx playwright trace open test-results/<thư-mục>/trace.zip
   npx playwright trace actions                         # danh sách bước, bước hỏng có dấu ✗
   npx playwright trace action <số của bước ✗>          # chi tiết lỗi
   npx playwright trace snapshot <số> --phase after snapshot   # cây accessibility lúc đó
   npx playwright trace close
   ```

5. Chạy lại riêng nó với Inspector: `npx playwright test --last-failed --debug` - bấm _Step over_ từng bước.

Trả chữ `3` lại như cũ, `npx playwright test --last-failed` → xanh.

## Bài tập 4 - Chạy lặp (3')

```bash
npx playwright test --repeat-each=3 --reporter=dot
```

Một test chỉ đáng tin khi xanh **3 lần liên tiếp**. Lệnh này là tiêu chí số 7 trong
[checklist chất lượng](reference/checklist-chat-luong-test.md).

## Bài tập 5 - Test chập chờn do **app** (8')

Config đang đặt `workers: 1`. Thử bỏ qua nó: chạy test mẫu _đặt hàng thành công_ 8 lần, 4 tiến trình song song.

```bash
npx playwright test e2e/shopping-flow.spec.ts -g "đặt hàng thành công" --workers=4 --repeat-each=8 --reporter=dot
```

Chạy 2-3 lần. Khi soạn bài, lần đầu **đỏ 3/8**, lần sau **xanh 8/8** - không ai sửa dòng nào. Đó là chập chờn.

Đi tìm nguyên nhân:

1. Nhìn terminal của `npm run dev`: có dòng `Error: ENOENT: no such file or directory, rename
   '.../storage/orders.json.tmp' -> '.../storage/orders.json'`?
2. Mở `src/features/orders/order-repository.ts`, hàm `writeAll`: mọi lần lưu cùng ghi **một** file `.tmp`
   rồi đổi tên. Hai đơn lưu cùng lúc → lần đổi tên thứ hai không còn file `.tmp` → lỗi 500 → test đỏ.
3. Kết luận: **lỗi của app**, không phải của test. Đây chính là nợ kỹ thuật _"Đơn hàng lưu file JSON,
   không an toàn khi ghi đồng thời"_ trong [FEATURE-BACKLOG.md](../FEATURE-BACKLOG.md) và NFR-1 của ý tưởng
   A ở Module 4-5.

> ⚠️ Ghi đồng thời có thể làm **hỏng** `storage/orders.json` (khi soạn bài đã gặp: JSON bị cắt giữa chừng,
> mọi trang đơn hàng lỗi 500). Thử xong thì xóa file - app tự tạo lại file rỗng:
>
> ```bash
> rm -f storage/orders.json storage/orders.json.tmp           # Windows: Remove-Item storage\orders.json*
> ```

Vì vậy config đặt `workers: 1`. Đó **không phải** "chữa cháy" cho test, mà là ghi nhận một giới hạn đã biết
của app. Sửa thật là sửa repository (Module 5, ý tưởng A, AD-4).

## Các hàm có sẵn sẽ dùng ở bài 6.4 - 6.6

| Nhóm               | Hàm                                                             | Ví dụ trên ShopLite                                                                       |
| ------------------ | --------------------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| Tìm phần tử        | `getByRole`, `getByLabel`, `getByText`, `getByTestId`           | `page.getByTestId("purchase-panel").getByRole("button", { name: "Thêm vào giỏ" })`         |
| Lọc                | `.filter({ hasText })`, `.filter({ has })`                      | `getByTestId("order-row").filter({ hasText: orderId })`                                   |
| Kiểm (tự chờ)      | `toBeVisible`, `toHaveText`, `toContainText`, `toHaveValue`, `toHaveCount`, `toBeDisabled`, `toHaveAttribute`, `toHaveURL` | `await expect(panel.getByRole("button", { name: "Tối đa" })).toBeDisabled()` |
| Gọi API thẳng      | fixture `request`: `.get`, `.post`, `.patch`                    | Tạo đơn bằng `request.post("/api/orders", { data })` trước khi kiểm hủy đơn               |
| Nghe mạng          | `page.waitForResponse`, `page.on("request")`                    | Chờ `PATCH /api/orders/<mã>` trả 200 rồi mới kiểm _Đã hủy_                                |
| Giả lập mạng       | `page.route` + `route.fulfill` / `route.abort`                  | Giả server trả 422 _"Mã giảm giá đã hết hạn"_ lúc đặt hàng (bài 6.6)                      |
| Nhiều tab          | fixture `context` + `context.newPage()`                         | Thích sản phẩm ở tab 1, tab 2 thấy ngay (bài 6.6, wishlist)                                |
| Dữ liệu trước khi trang chạy | `page.addInitScript`                                  | Ghi sẵn 50 sản phẩm yêu thích vào `localStorage`                                          |
| Đồng hồ            | `page.clock.setFixedTime`, `page.clock.install`                 | Chỉ đổi giờ **trình duyệt**, không đổi giờ server - nhớ khi kiểm mã hết hạn               |
| Ảnh so sánh        | `await expect(page).toHaveScreenshot()`                         | Lần đầu tạo ảnh gốc; đổi giao diện có chủ ý thì `--update-snapshots`                      |
| Tổ chức            | `test.describe`, `test.step`, `{ tag }`, `test.extend` (fixture), `test.skip(điều kiện, lý do)`, `test.fixme` | `test.step("giả lập mã vừa hết hạn", ...)` hiện thành một bước có tên trong báo cáo và trace |

✅ **Checkpoint:** chạy được 5 bài tập; biết lấy `trace.zip` của một test đỏ và đọc bằng cả giao diện lẫn
dòng lệnh; giải thích được vì sao Bài tập 5 đỏ là lỗi của app; `storage/orders.json` đã được dọn.
Không có gì để commit (nếu lỡ sửa test ở Bài tập 3, trả lại như cũ).

## Thảo luận

- `--retries=2` làm test chập chờn ở Bài tập 5 "xanh". Như vậy là tốt hay xấu? Khi nào nên bật
  `--fail-on-flaky-tests`?
- Nếu bạn là healer và chỉ thấy test đỏ ở Bài tập 5, bạn sẽ "sửa" test thế nào? Bản sửa đó che giấu điều gì?
